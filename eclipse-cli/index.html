Eclipse CLI

A terminal trading client for Solana memecoins, with a copy trader that monitors trades from any wallet and fires its own before the original has confirmed.

C++17 · Solana · Jito · Yellowstone gRPC

C++ client on GitHub

What it does

Eclipse is a terminal-based Solana trading client. It shows your holdings with size, average entry and current PnL, and it places buys and sells itself by building, signing, and sending each swap, routing it to pump.fun's bonding curve or to the Raydium pool the token graduated to.

Its copy trader watches a list of wallets. The moment one of them buys or sells, Eclipse decodes the trade, builds a matching swap and sends it, before the original transaction has even confirmed. Settings can be customized to decide how much to spend, the slippage, and which token types to copy. At the time, copiers this fast sold for thousands of dollars and almost nothing public explained how they worked, so I had to build my own from scratch.

Against a paid copier

To check the speed, a buy from Eclipse was also copied by a private copy trader that sold for thousands of dollars. The numbers below come from each tool's own logs in these two clips.

One run each, on different trades, so read it as the same league rather than a lab benchmark.

How it works

Speed was the whole point and every millisecond counted, so every step between seeing a trade and sending the copy was built to avoid waiting on the network.

  • Seeing trades before they confirm. Instead of polling an RPC node, the copier holds a Yellowstone gRPC stream open to a dedicated node. This is a validator plugin that pushes transactions out as they're processed. It subscribes at processed commitment and is filtered on the node to the watched wallets only, so a trade arrives as soon as a validator executes it, before the network has even confirmed it.
  • Decoding from the monitored transaction. Everything needed to copy a trade is already in the monitored transaction. Direction and size come from its token balance changes and logs, and as for Raydium, the pool and market accounts are extracted from the original instruction, so no time is spent on a pool lookup.
  • Nothing fetched on the hot path. A background task always keeps a fresh blockhash on hand, token accounts are derived locally, and the priority fee and compute budget are configured beforehand, so preparing and signing the copy only took 18 ms in the clip above.
  • Straight to the block engine. Copies skip preflight simulation and go to Jito's block engine as a bundle with a tip. The tip bids for priority placement in the current leader's block, and is either fixed or sized from Jito's live landed-tip percentiles.
  • Built from the wire format. Base58, ed25519 signing, program-derived addresses, shortvec prefixes and message compilation are all written by hand in about 600 lines of C++, with no Solana SDK. As a result, nothing can break on a version change, and nothing sits between the code and the bytes that reach the validator.
