Eclipse CLI

A terminal trading client for Solana memecoins, with a copy trader that spots a trade from any wallet it's watching and fires its own before the original has confirmed.

C++17 · Solana · Jito · Yellowstone gRPC

C++ client on GitHub

What it does

Eclipse is a menu-driven Solana trading client that lives in the terminal. It shows your holdings with size, average entry and live profit and loss, and it places buys and sells itself, building, signing and sending each swap and routing it to pump.fun's bonding curve or to the Raydium pool the token graduated to.

Its copy trader watches a list of wallets. The moment one of them buys or sells, Eclipse decodes the trade, builds a matching swap and sends it, before the original transaction has even confirmed. Its own settings decide how much to spend (a fixed amount, or the same size as the wallet it's copying, within limits), the slippage, and which venues to follow. At the time, copiers this fast sold for thousands of dollars and almost nothing public explained how they worked. This one was built from scratch.

How it works

Speed was the whole point, so every step between seeing a trade and sending the copy is built to avoid waiting on the network.

  • Seeing trades before they confirm. Instead of polling an RPC node, the copier holds a Yellowstone gRPC stream open to a dedicated node: a validator plugin that pushes transactions out as they're processed. It subscribes at processed commitment, filtered on the node to the watched wallets and the pump.fun and Raydium programs, so a trade arrives as soon as a validator executes it, before the network has confirmed it.
  • Decoding straight from the stream. Everything needed to copy a trade is already in the streamed transaction. Direction and size come from its token balance changes and logs, and for Raydium the pool and market accounts are lifted straight out of the original instruction, so there's no pool lookup, even the first time a token is seen.
  • Nothing fetched on the hot path. A background task keeps a fresh blockhash on hand, token accounts are derived locally, and the priority fee and compute budget are set up front rather than estimated, so preparing and signing the copy took 18 ms in the clip above.
  • Straight to the block engine. Copies skip preflight simulation and go to Jito's block engine as a bundle with a tip. The tip bids for priority placement in the current leader's block, and is either fixed or sized from Jito's live landed-tip percentiles.
  • Built from the wire format. Base58, ed25519 signing, program-derived addresses, shortvec prefixes and message compilation are all written by hand in about 600 lines of C++, with no Solana SDK. Nothing can break on a version bump, and nothing sits between the code and the bytes that reach the validator.
